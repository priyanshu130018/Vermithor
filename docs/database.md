# Vermithor Database & Vector Architecture

Vermithor uses PostgreSQL 16 enhanced with the `pgvector` extension for structured relational persistence and dense high-dimensional vector similarity indexing.

---

## 1. Domain Table Ownership by Service

Each microservice maintains bounded context ownership over its database entities and Alembic schema migrations:

```text
PostgreSQL 16 Database (`vermithor`)
│
├── Ingestion Service
│   └── `events`: Raw and processed telemetry event stream.
│
├── Incident Service
│   ├── `incidents`: Authoritative incident lifecycle entities.
│   ├── `incident_events`: Many-to-many associations between incidents and raw events.
│   └── `incident_timeline`: Ordered timeline milestones and status transition logs.
│
├── Anomaly Service
│   ├── `metric_observations`: High-frequency metric observation time-series records.
│   └── `anomalies`: Detected statistical and isolation forest anomalies.
│
├── Correlation Service
│   ├── `correlation_groups`: Co-occurring anomaly clusters within sliding temporal windows.
│   └── `correlation_signals`: Member signals linked to correlation groups.
│
├── RCA Service
│   ├── `rca_analyses`: Root cause analysis runs.
│   ├── `rca_candidates`: Scored root cause candidate rankings.
│   └── `rca_causal_edges`: Directed dependency edges in the causal graph DAG.
│
├── Log Intelligence Service
│   ├── `log_entries`: Sanitized log records with 384-d dense vector embeddings (`vector(384)`).
│   └── `log_templates`: Extracted invariant Drain message templates and cluster frequencies.
│
├── Retrieval / RAG Service
│   └── `runbooks`: Markdown operational runbooks with 384-d dense vector embeddings.
│
└── Summary Service
    └── `incident_summaries`: Evidence-grounded natural language incident summaries and JSON blocks.
```

## 2. Vector Indexing with pgvector

Dense embeddings generated by `sentence-transformers/all-MiniLM-L6-v2` (384 dimensions) are stored using pgvector's native `vector` data type:

```sql
CREATE EXTENSION IF NOT EXISTS vector;

-- Runbook semantic retrieval index
CREATE TABLE runbooks (
    id UUID PRIMARY KEY,
    runbook_key VARCHAR(64) UNIQUE NOT NULL,
    title VARCHAR(255) NOT NULL,
    service VARCHAR(64) NOT NULL,
    content TEXT NOT NULL,
    embedding vector(384),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Cosine distance similarity query
SELECT id, runbook_key, title, content, 1 - (embedding <=> :query_embedding) AS similarity
FROM runbooks
WHERE 1 - (embedding <=> :query_embedding) > 0.65
ORDER BY similarity DESC
LIMIT 5;
```

## 3. Database Schema Migrations (Alembic)

Every microservice contains an isolated `migrations/` directory and `alembic.ini` file:

```bash
# Example: Apply database migrations for incident service
cd backend/services/incident
alembic upgrade head
```

In containerized deployments, migrations are executed automatically during container startup or via Kubernetes `db-migration-job.yaml` prior to serving traffic.

---

## 4. Connection Management & Resilience

- **Connection Pool**: SQLAlchemy `QueuePool` with standard connection recycling (`pool_recycle = 1800`, `pool_size = 10`, `max_overflow = 20`).
- **Disconnect Handling**: `pool_pre_ping = True` enabled across all services to transparently detect and replace stale or dropped database connections without crashing active HTTP requests.
- **In-Memory SQLite for Automated Testing**: Tests run against in-memory SQLite instances using `StaticPool`, avoiding external PostgreSQL database requirements for unit and integration suites.
